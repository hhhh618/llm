# 从事件风暴到领域模型：设计与验证指南

用于把已发现的业务事实、分歧和场景转成可讨论、可验证的模型。按问题复杂度选择深度：单个功能可只细化相关上下文与聚合；跨业务流程再展开上下文映射。不要为填满模板而虚构业务规则，也不要将便利贴的空间分组自动视为最终设计。

## 工作原则与输入

- 输入包括目标、范围、业务参与者、事件时间线、命令、政策、例外和热点，以及已有规则、文档或代码证据。保留来源、版本、业务负责人和确认状态。
- 区分 **已确认事实 / 推断或提议 / 假设 / 待决问题**；对推断标理由，对冲突保留各方说法及来源。示例只能作为启发，不自动成为用户的规则。
- 从业务语言、行为与决策出发；表、类、接口和服务拆分是后续选择。模型服务于共同理解和解决业务问题，领域专家负责确认业务语义与规则。
- 在合适的时间重新审视事件风暴结果：找到缺口或矛盾时回到场景，避免将一次探索当成不可更改的需求。

## 1. 愿景、范围与统一语言

1. 用业务目标、价值、参与者、起止边界和明确不做的事项描述本次范围；记录建模目标及其决策用途。
2. 选取能解释业务的端到端场景，列成功、拒绝、取消、超时、并发、补偿等实际适用的变体；不适用的无需强加。
3. 维护每个上下文内的术语表：`术语 | 定义 | 所属上下文 | 示例/反例 | 同义词/歧义 | 来源与状态`。同一个词在不同上下文含义不同时保留两种定义，并标识转换，不强行合并。
4. 对尚无依据的目标、规则、边界与异常明确标为假设或待确认。确认可由领域专家走查真实案例完成，AI 提出的候选不是业务事实。

## 2. 战略设计：子域、限界上下文和关系

### 子域与上下文

- 按业务能力识别候选子域，讨论哪些能力构成差异化的 **核心域**、哪些是必要但非差异化的 **支撑域**、哪些可采用通用方案的 **通用域**。分类是针对特定组织和目标的判断，会随战略变化。
- 限界上下文是模型与语言保持一致的边界；子域是业务问题空间，二者不要求一一对应。根据术语含义变化、业务责任与决策权、规则及生命周期差异、团队协作和集成需求提出候选边界。
- 每个候选上下文描述：目标和职责、包含/排除的概念与决策、主要角色、拥有的数据与行为、对外提供和依赖的信息、负责人及待确认项。用事件流中的语言变化与真实场景检验，时间线分段只能作为线索。
- 限界上下文不是自动等同于微服务、数据库、团队或部署单元；部署选择要结合组织、演进和运行约束。

### 上下文映射与集成契约

- 对每一条实际关系记录：上游/下游及方向、业务目的、交换的信息、发起时机、消费者需要、语义转换、责任人、失败与恢复路径。模型关系按真实协作选择，如 Partnership、Customer–Supplier、Conformist、Open Host Service/Published Language、Anti-Corruption Layer；不要机械套用。
- 对同步查询、命令或异步通知说明为何采用、成功与失败的业务含义、超时和重试、重复及乱序处理、版本兼容、可观测性与数据敏感性。不同上下文的同名状态不能默认等价。
- **领域事件**描述某上下文内部有业务意义的事实；**集成事件**是经筛选、适合跨边界发布的稳定契约。只有确有消费者需求的事件才需要对外发布；记录事件名、发生时刻、业务标识、必要载荷、来源、版本和语义。别把内部对象结构直接当作永久契约，也不要包含不必要的敏感信息。
- 对有可靠传递需求的异步流程，按实际保障选择事务性发布/Outbox 等机制；同时设计消费者幂等、重复与乱序处理、死信或人工恢复。消息发布与事务提交的先后要避免将已回滚的事实对外宣布。交付保证依赖具体基础设施，不承诺天然恰好一次。

## 3. 战术设计：由行为与一致性推导模型

1. **从场景找行为。** 对重要命令写出发起者、意图、目标、前置条件、决策规则、成功事实和拒绝原因；区分命令（请求）与事件（已发生的事实）。一个命令不一定成功，也不必机械地恰好对应一个事件。
2. **识别实体与值对象。** 有跨状态变化仍需追踪的业务身份和生命周期者可作为实体；按属性描述、以值相等判断且通常不可变的概念可作为值对象。某概念采用何种建模方式取决于上下文和用途，不因其名词形式自动成为实体。
3. **提出聚合边界。** 问“哪些业务约束必须在一次决策完成时立即成立，谁负责保护？”据此识别根及其内部对象，记录根的唯一标识、生命周期、行为、状态变化和不变量。聚合是需要立即维护的业务一致性边界，并非对象导航图或数据表集合；优先保持边界足够小，但以实际不变量为依据。
4. **给每条规则定作用域。** 对每个不变量写出条件、适用状态、例外、时间点、数据来源以及哪个决策者负责。不要把跨多个聚合或外部系统的数据约束，未经证明地声称由单一聚合根保证。存在跨边界强一致需求时，进一步论证边界、事务或业务协议；允许延迟时明确窗口、冲突处理、补偿和责任。
5. **选择其他模式。** 无法自然归属单一实体且确有领域意义的行为可用领域服务；复杂创建可用工厂；需要持久化聚合时可用仓储接口。应用服务负责协调事务和用例，基础设施实现技术细节；具体分层和模式按复杂度选用，不是所有项目都必须引入。
6. **识别读需求。** 对每个决策标出参与者需要看到的信息、数据来源、时效要求与权限。读模型是为查询或决策服务的表示，不自动等于独立数据库或强制采用 CQRS。

### 建议的聚合卡

```text
上下文 / 聚合名 / 根标识：
职责与生命周期：
内部实体和值对象：
命令 | 前置条件 | 决策/不变量 | 成功事件 | 拒绝或异常：
跨聚合或外部依赖及一致性要求：
相关场景、规则来源、待决问题、确认人/状态：
```

事件卡至少包括名称（业务过去时）、发生条件、业务含义、主体标识、关键属性与来源；命令卡至少包括意图、发起者、目标、前置条件及可能结果。具体载荷和接口以业务需要确定。

## 4. 场景验证、追溯和交付

- 与领域专家逐步走查真实案例：`起始状态/上下文 → 角色和触发 → 命令 → 决策与不变量 → 事件或拒绝 → 策略/后续动作 → 最终状态与可观察结果`。至少验证一条主要成功路径；按风险选择边界、异常、取消、超时、重复、并发或补偿等路径。
- 提问：规则是否有明确负责人？失败后是否产生相应事实？事件是否有真实消费者？重复或乱序如何影响业务？哪些状态可能短暂不一致？语言是否在边界处改变？存在冲突时保留热点、责任人和下一步，不代替专家裁定。
- 建立轻量追溯：`业务目标/来源 → 场景 → 事件与命令 → 上下文 → 聚合行为/规则 → 验证示例 → 代码或测试（如已存在）`。每项保留确认状态；证据缺失标待验证，不能宣称模型已验证。
- 将确认的规则落为具体的 Given–When–Then 或例子表，覆盖允许、拒绝和重要边界；检验断言是否可观察且来自业务规则。若没有执行测试，明确是测试设计而非测试通过。
- 最小交付可按任务裁剪，复杂任务通常包括：范围与假设、术语表、事件时间线及热点、子域与上下文职责、上下文图与集成关系、聚合卡、关键规则及场景验证、待决问题和下一步。图仅用来解释关系，应能与文字和场景互相核对。

### 小例子（仅演示，均需项目确认）

假设某业务规定“未取消订单才能确认支付”，且支付由独立上下文处理。订单域可能接收 `确认订单支付` 命令；若订单已取消则拒绝，否则记录 `订单支付已确认`。支付上下文的 `支付已完成` 是否触发该命令属于候选策略；若支付完成通知迟于取消，如何退款或人工处理必须与业务确认。事件发生顺序、事务边界、跨系统退款保障均不能仅凭这个例子推定。金额如何计算、库存何时扣减同样需要另有依据。

## 常见错误与纠正

- 把事件列表直接翻译成类表，忽略角色、决策、例外和因果：回到场景与业务规则。
- 把时间线上的分组或名词直接当作上下文、聚合或微服务：用语言边界、职责与一致性要求验证。
- 把频繁一起变化当成必须强一致，或把整条流程放进一个大聚合：逐条说明在何时必须成立及其所有者。
- 把所有规则放在应用服务，或把外部系统调用塞入聚合：将稳定的业务决策放到合适的领域对象，并显式协调外部依赖。
- 假设事件天然可靠、有序、不重复，或把领域事件等同事件溯源：根据可靠性需求设计契约和恢复；事件风暴不要求采用事件溯源、CQRS 或微服务。
- 过早固定状态、字段和标准流程：保留冲突、证据与假设，使用真实例子迭代并请领域专家确认。
