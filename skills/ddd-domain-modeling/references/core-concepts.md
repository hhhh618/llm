# 核心概念：用判别问题减少歧义

下表是建模时的简要工作定义，依据见 [来源](sources.md)。定义用于提出问题，实际业务规则仍须从场景和领域专家处确认。

| 概念 | 工作定义 | 判别问题 / 易混点 |
|---|---|---|
| 领域 Domain | 软件要帮助解决问题的业务或专业活动范围 | 我们帮助谁完成什么工作？领域也可以是网络管理或测试诊断 |
| 子域 Subdomain | 为理解问题而识别出的相关能力或知识部分 | 它贡献什么能力？核心、支撑、通用的判断相对于当前组织的战略价值 |
| 领域模型 Domain Model | 为当前用途选择并组织起来的领域知识表达 | 能否解释行为和规则？模型不是业务现实的完整复制，也不是仅列数据字段 |
| 限界上下文 Bounded Context | 某个模型和统一语言具有明确含义的适用范围 | 相同身份、状态、行为和规则在此是否相容？它属于解决方案的模型边界 |
| 统一语言 Ubiquitous Language | 领域专家与开发者基于模型共同使用、持续修正的语言 | 能否用它讲清真实场景，并在需求、代码和测试中表达相同含义？不是全公司的强制词典 |
| 实体 Entity | 通过身份延续来识别的对象 | 属性全变了是否仍是同一个？数据库主键的存在本身不足以证明业务实体 |
| 值对象 Value Object | 用属性值表达含义、按值等价的对象 | 两份相同金额和币种是否可互换？通常建成不可变对象，变化时整体替换 |
| 聚合 Aggregate | 围绕需要共同保持的规则组织的一致性边界 | 哪些变化必须一起成功才能不违反规则？它不是全部关联对象的导航图 |
| 聚合根 Aggregate Root | 聚合对外的身份入口和规则守门者，本身是实体 | 外部能否绕过它修改内部状态？根可委托内部对象计算，但仍维护整体不变量 |
| 不变量 Invariant | 规定范围内，在允许观察到的有效状态中始终成立的业务条件 | “已发货数量不得超过指令数量”由哪个边界原子维护？不是泛指输入格式校验 |
| 命令 Command | 请求执行某项行为的意图 | 谁请求什么？可能因前置条件不满足而被拒绝；收到请求不等于业务已完成 |
| 领域事件 Domain Event | 模型关心的、已经发生的业务事实 | 对象状态如何因此改变？不是每条技术日志；是否异步不决定其领域含义 |
| 集成事件 Integration Event | 对其他上下文公开的事实契约 | 谁能依赖哪些已提交事实？可由领域事件投影而来，不直接暴露内部对象图 |
| 领域服务 Domain Service | 不适合归属某个实体或值对象的领域运算 | 是否表达业务规则？不要把本应属于聚合的行为全部搬到 Service |
| 应用服务 Application Service | 协调一个用例的执行 | 负责加载、调用、保存及边界交互；业务资格与状态规则应由领域模型决定 |
| Repository | 从领域视角获取和保存聚合的抽象 | 是否保持聚合边界和生命周期？不是每张表一个 DAO；查询投影可另行设计 |

领域 / 子域描述问题，限界上下文描述模型适用范围，进程、容器、数据库和微服务描述实现与部署。不要假设它们一一对应：一个业务子域可能有多个模型，一个模块化单体可以包含多个上下文。以实际语言和规则检验模型边界，再结合负载、团队协作与故障隔离选择部署方案。

子域分类用于决定建模投入：**核心子域**承载当前组织的关键差异化能力；**支撑子域**提供本业务所需但不形成主要竞争差异的能力；**通用子域**解决广泛共有、已有成熟做法的问题。分类随组织和战略变化，不表示某类功能永远重要或不重要；也不直接决定由几个团队、几个服务来实现。

建模时同时记录概念的反例。例如“账户”若被定义为登录凭证，就不能悄悄加入账本余额的含义；即使它们都引用同一个自然人，也需要明确关系和各自的权威来源。

## 从概念到代码的责任分配

先尝试将行为放到能说明该规则的实体或值对象中；确实跨对象且无自然归属的运算，再使用领域服务。领域服务可依赖领域所需的接口，不把数据库表、HTTP DTO 或特定 ORM 的规则当成领域概念。

应用服务协调“加载订单 → 请求确认 → 保存结果”，订单判断“当前状态是否可确认、数量是否有效”。Repository 的接口应支持该聚合的操作需要；并发版本、事务和持久化映射由实现落实。简单只读报表无需为使用 DDD 强行还原全部聚合。

领域事件与集成事件可以共享某些事实，却有不同演进责任。内部事件可随内部模型变化；公开契约需考虑消费者、版本和提交可见性。采用事务内处理、异步处理或 Outbox 等机制时，解释所保证的原子性和失败恢复范围，不以模式名称代替保证。
