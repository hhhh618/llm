# 上下文划分与概念一致性

## 以冲突和责任发现边界

从一条端到端流程收集证据，比较候选模型：

| 观察维度 | 应问的问题 | 支持分界的信号 |
|---|---|---|
| 语义 | 同一个词在这里究竟指什么？ | 词相同，但纳入模型的属性与行为不同 |
| 规则 | 谁决定资格、额度、可执行操作？ | 同一数据在两处有不同合法性判定 |
| 身份与生命周期 | 何时创建、替换、结束？何为同一个？ | 一处结束后另一处仍有独立业务过程 |
| 所有权 | 谁对哪类事实负责，谁有权修改？ | 有明确、可协商契约的独立模型责任 |
| 变化原因 | 哪类需求会让模型改变？ | 共享模型不断迫使无关规则同步修改 |

这些是证据，不能机械计分。相同团队可以维护多个上下文；多个团队共享一个上下文则需要主动协调语言和模型。现有部门、数据库和服务边界是约束与现状，不自动等于合理边界。

对候选边界写一条可推翻的理由：“销售订单确认金额承诺；履约订单控制实际出库，两者生命周期和不变量不同，因此分开建模。”再拿实际反例挑战它。划得过细会增加翻译与协作成本；同一条必须原子维护的规则被拆开，通常需要重审边界或明确业务协议。

## 上下文映射要表达可执行语义

先画上下文及交互，再标明关系。上游 / 下游表示契约影响和依赖方向，不等于每条消息的传输方向。按真实协作选择关系：共同演进可用 Partnership；下游能协商需求时考虑 Customer/Supplier；只能接受上游语义时是 Conformist；需要保护本地模型时建立防腐层（ACL）。共享内核只共享明确、共同维护的小部分模型；公开 API 和发布语言用于稳定边界契约，不表示共享全部领域对象。

对重要交互写清以下内容即可，无需额外建一套文档系统：

- 谁提供哪类权威事实，消费者以什么本地含义使用。
- 身份是否等价；一对一、一对多或多对一时如何关联，哪个 ID 只作追踪键。
- 状态、单位、币种、时间、枚举和缺失值如何转换。
- 哪些信息被有意舍弃，舍弃后还能支持哪些决策；不能表示或不能确认的输入如何拒绝、隔离、补充或人工处理。
- 提交可见性、重复、乱序、版本兼容、失败和恢复由谁处理；消费者成功是否需要向业务反馈。

不要将缺失默认为零、将未知状态映射为成功，或只因字段名相同就直接复制。映射不可逆时，明确保留来源引用以及不支持反向还原；需要原始事实的决定应回到事实所有者。

## 概念一致性比命名一致更深

《设计原本》讨论 conceptual integrity，即整体设计的概念连贯性及用户理解和使用的一致体验。它不是 DDD 术语定义来源。将其落实为“上下文内保持统一模型、上下文间显式翻译，并保证整体体验可解释”，是本技能采用的工程衔接，不能说成 Brooks 原文提出了 DDD 方法。出处与支持范围见 [来源](sources.md)。

一致性评审可以沿一个概念追踪：

| 检查面 | 发现矛盾的例子 | 应做的修正 |
|---|---|---|
| 身份 | 文档按合同号认定同一订单，代码按收件地址合并 | 明确订单身份与地址值对象，阻止错误合并 |
| 状态与生命周期 | API 的“完成”是接单成功，界面解释为已送达 | 分清销售确认与履约完成，展示正确业务进度 |
| 行为与权限 | 规则禁止确认后改价，后台接口仍直接改金额 | 通过受约束的领域行为修改，核验所有入口 |
| 不变量 | 测试只校验数量为正，遗漏累计发货上限 | 将累计规则放在一致性边界，并验证并发行为 |
| 跨上下文映射 | 销售取消被直接视为仓库已停止发货 | 建立停止请求、结果反馈和竞争情形处理 |

保持内部一致不意味着全局统一一个大对象，也不意味着允许对用户呈现互相冲突的承诺。一个事实从何处来、当前同步到哪一步、失败时代表什么，都应能用业务语言说明。

对无法同时满足的说法，先保留冲突证据和规则所有者，找出是命名问题、模型问题、边界问题还是未决业务政策。不要只改名掩盖矛盾，也不要以“最终一致”解释永远无法履行的业务保证。
