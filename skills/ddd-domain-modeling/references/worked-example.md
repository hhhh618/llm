# 可演练示例：两种“订单”

以下是原创教学场景，业务政策均为示例假设。它展示如何从同词异义推导边界、映射和验证；实际项目须用自己的规则替换。

## 场景与两个模型

商家接受顾客购买商品的请求，再安排仓库出库。为聚焦语义，本例只处理实物商品、不拆分跨仓履约，不讨论付款和退货。

| | 销售上下文 | 履约上下文 |
|---|---|---|
| “订单”的含义 | 顾客与商家达成的商品、数量和价格承诺 | 按指令将指定商品交付给收件人的作业 |
| 根及身份 | `SalesOrder`，`salesOrderId` | `FulfillmentOrder`，`fulfillmentOrderId`；`sourceSalesOrderId` 只关联销售事实 |
| 关键值对象 | 数量、金额与币种、确认时收货地址快照 | 数量、地址快照 |
| 内部对象 | 以 `lineId` 标识的销售行 | 以销售行引用关联的履约行、发货记录 |
| 生命周期 | 草稿 → 已确认 | 待出库 → 部分发货 → 已发完 |
| 规则与所有者 | 销售决定成交内容与确认资格 | 仓储团队决定可处理 SKU、出库资格及累计发货量 |

分界理由：销售关心成交承诺，履约关心实物作业；二者身份、状态与规则不同。共享一张“订单”表会使“确认”和“完成”混杂。两个上下文可以先部署在同一应用中，保留模块和契约边界。

## 聚合内的不变量

本例规定：

- **销售根：**确认时至少有一行，每行数量为正整数，金额币种一致、订单总额非负；确认后商品、数量、金额和地址快照不可直接修改。是否允许修订须另定业务流程。
- **履约根：**至少有一行且每行指令数量为正整数；对每行 `0 ≤ 累计已发货数量 ≤ 指令数量`；全部行发完才进入“已发完”。一次发货的数量更新与发货记录共同提交。

两者不共享一个跨上下文不变量。销售“已确认”表示承诺已成立，不表示仓库已接单或已经发货。应用读模型可以展示“销售已确认，履约待接收”，不要合成一个含糊的“完成”。

## 命令、事实与映射契约

1. 应用服务加载销售订单，调用 `确认订单`。根验证规则，成功后记录内部领域事件 `销售订单已确认`；不合法的命令被拒绝，状态保持草稿。
2. 销售事务成功时可靠登记公开事件 `SalesOrderConfirmed.v1`。若用 Outbox，则业务变更和待发布记录同事务；发布失败可重试，不能据此声称消费者已成功。
3. 公开契约包含 `eventId`、`schemaVersion`、`salesOrderId`、销售确认版本、确认时间、行引用 / SKU / 数量、金额币种和收货地址快照。本例发布价格用于追踪销售承诺，履约不据此决定发货。
4. 履约防腐层将消息翻译成 `建立履约订单` 命令，建立本地身份，保存来源关联。履约根验证本地规则；内部事件 `履约订单已建立` 与对外接收结果属于不同契约。

销售是成交事实的上游，履约是其消费者；接收结果可反向传输，不因此颠倒该事实的依赖关系。假设双方能协商公开契约，可按 Customer/Supplier 协作；履约以 ACL 隔离自身模型。

| 映射项 | 处理规则 | 丢失或拒绝的含义 |
|---|---|---|
| 销售 ID → 履约 ID | 新建本地 ID，以来源 ID 建唯一关联；本例一个销售订单最多建立一个履约订单 | 两个 ID 不互换；未来拆仓时应升级为一对多，不能沿用该假设 |
| 行 ID / SKU / 数量 | 保留行引用和数量，验证 SKU 可履约且数量有效 | 未知 SKU、重复行 ID、零或负数量：隔离并返回有原因的拒绝，不能静默跳过该行 |
| 地址 | 使用确认时完整快照，不读取顾客后来修改的默认地址 | 缺少必需地址字段则拒绝；不能猜测或默认发往旧地址 |
| 金额和币种 | 履约不建价格模型，不写入履约聚合；保留来源事件引用以供追溯 | 信息被有意舍弃，不能从履约订单还原成交价，也不能据此计算退款 |
| 销售“已确认” → 履约状态 | 验证通过才建立“待出库” | 绝不映射为“已发完”；没有一套共享状态枚举 |
| 未知契约版本 / 枚举 | 隔离并报告不支持，待明确兼容策略后处理 | 不映射成默认成功状态 |

来源引用需指向可访问的事件存档或业务事实接口，并具有满足追溯需求的保留策略；一个无法解析的 `eventId` 不等于保留了证据。

## 失败、重复与并发

履约把消费记录与建立聚合共同提交，以 `eventId` 去重，并对来源 ID 保持唯一约束。相同事件重复到达返回原结果；同一来源 ID 携带不同确认内容则报告冲突，不能覆盖已有指令。销售确认版本用于识别内容身份，消息时间戳不作为“最后写入获胜”的依据。

本例确认后不接受修订事件，未知修订必须隔离。若未来加入版本化修订，要定义缺失前序时的等待、补取或拒绝以及业务超时反馈，再放开乱序处理。单靠事件排序字段不会自动实现顺序保证。

履约拒绝不会抹去销售已确认的事实：系统明确反馈“履约接收失败”及原因，由责任人修正 SKU 配置后重新处理原事件，或进入另行定义的业务处理流程。去重记录区分成功、暂时失败和终止拒绝；修复后允许显式重试，不能因记录过 `eventId` 就永久忽略失败。接收成功的决定性状态和消费记录必须原子保存。

仓库连续发送两笔出库命令时，聚合版本控制或等效事务保护累计上限。例如指令数量为 3，两笔各发 2，并发成功两笔会违反不变量；应只有一笔提交，另一笔重新读取后被拒绝。仅在 UI 上禁用按钮不足以保护规则。

## 最小演练

| 输入 / 前提 | 可观察结果 | 检验什么 |
|---|---|---|
| 草稿一行数量 3，合法价格与地址 → 确认 | 销售已确认；履约收到后建立待出库指令 3 | 正常路径、分阶段承诺 |
| 同一公开事件到达两次 | 仍只有一个履约订单，返回同一接收结果 | 重复和身份 |
| 事件内一行未知 SKU | 不产生缺行的履约订单；销售仍已确认，显示接收失败 | 翻译拒绝、部分成功反馈 |
| 确认后通过后台直接改价格 | 被规则拒绝；履约模型也不能提供退款金额 | 行为一致性、信息损失边界 |
| 指令 3，并发请求各发 2 | 累计不超过 3，其中至少一笔失败 | 聚合不变量与并发 |
| 未知 v2 修订先到达 | 隔离并报告，不覆盖 v1 指令 | 契约版本和乱序 |

评审时让参与者用两种语言分别讲完同一条流程。若有人说“订单完成”却无法指出是哪一个上下文、何种状态及哪些事实支持，应回到概念定义，而非先补一个布尔字段。
