# 方法如何进入同一条工作流

SDD 在本技能中指规格驱动开发，ADD 指属性驱动设计。下面是本技能的组合方法，不是宣称这些理论共同规定了一个标准流程。

| 方法 | 本次用在什么地方 | 实际产物与核验 |
|---|---|---|
| DDD | US 之前澄清范围、上下文、概念及规则；理解变化后回到模型修订 | 有归属的领域词、身份/状态/不变量、上下文翻译；用真实场景及反例演练 |
| SDD | 把本次意图形成持续维护的规格，并指导实现和变更分析 | 有稳定身份及版本的 US/AC/TC、实现关联；比较前后快照，不让代码变化静默改掉承诺 |
| BDD | 用业务语言与具体实例发现含混、讨论结果 | 可讨论的 AC 与 Given–When–Then 实例；检查观察结果能否区分符合与违背规则 |
| ADD | 质量属性及外部约束影响架构时，分析驱动因素、策略与取舍 | 质量属性场景、AC、测量型 TC、架构理由；不把所有质量属性硬改成用户故事 |
| TDD | 适用的行为实现中，用短反馈推动代码设计与重构 | 有意义的失败、最小实现、通过与重构；测试判据源于业务承诺，不能迎合代码改预期 |
| XP | 支撑小步实现、持续集成、重构及协作 | 复用项目已有工程实践和反馈，按任务需要组合，不要求一次引入全部实践 |
| 敏捷 | 以小增量交付和反馈持续纠正理解与计划 | 本次切片、运行结果、用户反馈与下一轮变化；可工作的软件与价值反馈优先 |

## 相互关系与边界

**范围/上下文/领域词 → US → AC → TC → 实现与执行证据** 是主要追踪路径。规则可支持多个 US/AC，AC–TC 也是多对多；直接源于范围内规则或质量属性的 AC 可以没有 US。不要把表的上下顺序当成完整项目必须一次通过的瀑布阶段。

领域模型解释“这些对象和行为意味着什么”；US 表达目标与价值；AC 表达可接受的承诺；TC 表达具体检验设计；execution 记录实际观察。名称一致只是检查入口，概念身份、状态转换、行为与不变量也要一致。

契约、状态机、OpenAPI、Gherkin 或现有测试框架可继续使用，用 ID 与 manifest 建立定位关系，无需全部改写成本技能的 JSON。JSON 是最小可检查清单，不能完整表达所有架构、领域模型或形式化证明。

当前 AI 工具各有自己的 SDD 流程和持久化方式；本技能选择持续保留规格、保守判定旧证据失效、由主 Agent 整合共享规格。这些是工程约定，不是 SDD 的统一语法或外部标准。定义来源见 [一手来源](sources.md)。
