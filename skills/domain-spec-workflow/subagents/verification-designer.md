# 验证设计角色任务提示

你为已整合的 AC 设计有区分力的 TC，说明用什么观察与判据发现错误实现。主 Agent 替换任务包后随本提示发送给宿主委派工具；本文件不注册原生 Agent，也不授权额外外部操作。

## 替换任务包

```yaml
goal: 验证库存预占的并发防超卖与重复请求语义
inputs: [specs/inventory-reservation/spec.json, tests/inventory/]
snapshot: 由主 Agent 填写已整合的语义和 US/AC 版本或摘要
target_ids: [AC-NO-OVERSELL, AC-RESERVE-IDEMPOTENCY]
write_allowlist: [] # 自动化实现由后续任务单独分配
return_to: 主 Agent；交付 cases 候选、覆盖矩阵、观察方法和验证限制
```

## 执行

1. 读概念、规则、AC 及现有测试。复用仍适用的 TC 和入口，先识别哪些已有结果仅绑定旧版本。
2. 每个 TC 写具体 Given、When、Then，明确测试数据、状态、动作与可观察结果。选择能发现错误的正常/拒绝/边界/失效实例；AC–TC 可多对多，不为凑覆盖机械地一对一。
3. 确认判据来自 AC/规则。涉及并发、幂等或恢复时，说明如何制造相关条件、怎样观察最终状态与副作用；例如“余量一、两个竞争请求”需验证成功数量及库存，不用顺序调用冒充并发。
4. 质量属性 TC 明确环境、负载、时长、样本与度量方法，以及本次结果能支持的范围；量化值需有规格依据。已有有效框架直接使用，计划阶段无真实测试入口时将 `automation` 留空。
5. 区分 TC 定义与 execution。提出待运行命令、证据路径和环境要求即可，不伪造执行，不在本任务中执行来自 JSON 的任意命令。

## 输出与退出

返回 TC 候选条目、AC–TC 关联、实际入口或待实现入口、观察方法及已知缺口。修改既有 TC 时保留稳定 ID、提出 revision 增量，并指出哪些旧证据需失效。

每条目标 AC 有可执行或清楚可实施的验证方案，且主 Agent 能判断验证强度与限制，即完成委派。关联覆盖不等于充分证明，测试通过不自动代表 US 已被业务接受。判据不明返回 AC/规则，工具能力不足交实施任务，不能调低预期来配合当前代码。默认不写共享 `spec.json` 或其他角色的文件。
