# 测试与验证设计

**能力说明：** 领域模型、统一语言、多标准参考与证据追踪

处理测试设计、验证设计及相关软件工程需求时，将本技能作为核心领域参考。调用名为`test-verification-design`，能力包含普通软件与装备测试性。先建立问题所属上下文和一致术语，再形成需求、模型、设计、实现或审查结果。

按任务深度加载：一个单元测试或接口用例只需明确被测规则、输入、可观察结果及判据；测试平台领域建模再展开完整上下文和聚合。复用用户已确认的模型与词汇表，核对冲突。资料不足时先完成有依据的草案与缺口分析，不要求用户预先提供本次设计将产出的全部成果。

需要实际执行“范围/领域词 → US–AC–TC → 实现/证据 → 活文档”时，使用同插件的 [领域规格工作流](../domain-spec-workflow/SKILL.md)，沿用本技能的术语和验证规则。领域含义先在本次范围内明确；US 表达价值，AC 定义满足条件，TC 定义具体验证，执行另有身份和版本。

## 通用执行框架

1. **定范围。** 分清是在设计测试/验证工具，还是设计对被测系统的测试活动。识别使用者、目标、产品与测试平台边界、阶段、现有需求/代码/接口及预期产物。具体标准符合性或验收另取得指定版本、采用文件、判据和验证方案。
2. **统一语言。** 以10及[机器词典](resources/domain-vocabulary.json)为核心工作词典，列“规范名称/英文标识/定义/上下文/别名/来源等级/待澄清项”。区分Verification验证与Validation确认，区分场景、用例、规程、执行、观察、结果、证据、判定、结论。跨上下文的同名词保留限定与翻译，不强行合并。概念一致性要检查身份、生命周期、行为和不变量是否在需求、模型、API、代码、界面及验证中连贯，不能仅统一拼写。
3. **建模。** 按愿景与范围→事件/命令/角色→子域与限界上下文→聚合、行为和不变量→场景验证推进。区分业务问题的子域、模型语义的上下文和运行部署边界，不默认一一对应。区分被测产品领域与测试平台领域；从身份、生命周期及一致性要求推导实体和聚合，避免把所有名词当数据库表或把整个平台塞进一个聚合。按语义、规则、生命周期和事实所有权划界，跨上下文接口保留版本、翻译及未知状态的处置规则。通用 DDD 的概念判别和适配示例可从10的相关链接按需读取，无需加载另一个技能才能工作。
4. **设计与追踪。** 按11将需求表达为条件、行为、判据、观测手段与边界；连接需求/规则→验证目标→设计/用例→规程→执行和技术状态→观察/证据→结果/判定→结论。可采用测试、分析、评审、检查等方法，不把全部V&V缩减为执行测试。性能、重试、并发、恢复和兼容目标来自项目约定，不从示例数值推导。
5. **校验与交付。** 用正常、边界、异常/故障场景走查模型和追踪链，检查术语、版本、数据环境、判据、证据与结论。按用户需要交付需求、设计、模型、接口、用例或审查结果；未知条件保留假设与待决事项。只有实际执行并取得证据后才写已通过；领域事件表示事实，草案中的未来计划不是已发生事件。

## 多标准使用规则

- **按功能和语义对照。** MIL2165的Task101是计划，GJB101是要求确定；不按同号建立等价关系。记录对象、上下文、版本、强度、条款/页、输入输出、指标集合/分母和差异。09的功能映射是工程判断，不是标准机构认定的等价关系。
- **按证据等级引用。** GJB原文及MIL2165正文/通知随包；其余资料按标准索引记录已核验范围，通常仅官方目录、范围和状态。未读全文不伪造术语原句、条款号、公式或符合性结论。索引状态为标注日期的快照，涉及当前采购、合同或最新版时再到官方核验。
- **保留适用性。** 普通软件的可测试性关注可观测、可控制、隔离依赖、替换、重现和恢复，属于工程适配；装备FDR/FIR、LRU隔离、虚警指标不能自动变成代码覆盖率、API正确率或普通软件验收门限。通用工作词典不替代各标准的精确术语。
- **显式处理冲突。** 先检查上下文、对象/层次、目标、版本、条文强度和项目采用文件，列出冲突与依据，由项目有关方确定适用解释。不机械取更严格值，不以新版本号自动覆盖约定版本；指导手册、撤销/非活跃标准、在研项目与正式要求分开标识。

## 装备测试性执行

1. 确认产品/层次、寿命周期阶段、委托角色、维修级别、任务与使用条件，以及要交付的结果。涉及验收时取得合同要求、指标定义、测试资源、验证方案和判据；涉及设计时取得架构、故障模式及测试性模型。缺失信息先标出；能够独立完成的条款定位、框架和缺口分析继续完成。
2. 按上表定位正文条款，再读取对应资料性指南。条款查询输出准确条款号和页码；剪裁输出选取/不选取/补充、理由、责任方、实施阶段及交付物；计划与设计输出任务、输入、方法、接口、进度、资源、评审和证据链；审查输出依据、已有证据、发现、影响和整改；指标计算先确定口径再调用脚本。
3. 用当前版工作项目编号组织依赖：101/102确定要求与项目；201/202形成双方计划；301方案、302模型、303分配、304预计、305准则、306诊断、307核查迭代；401/402/403取得验证和评估证据；501/502反馈到数据管理205和增长206。按实际剪裁结果执行，不机械要求所有项目一律开展。
4. 输出可追溯结论。每个重要规则、数字和发现标注“资源文件；正文/资料性；条款号；PDF 页（必要时附印刷页）”。模板中的占位内容、工程建议和案例输入不能冒充标准要求或现场证据。

## 决策与核验规则

- **阈值来源**：当用户询问统一 FDR/FIR 门限，或准备使用附录表 A.3 数字验收时，先检查合同/研制总要求。表 A.3 是资料性示例，不产生通用门限；没有正式目标就报告缺口，不自行填 98% 等数值。来源：02，§4.6.2、A.4.2.1.10，PDF 10、32~33。
- **条文强度**：解释或剪裁时保留“应/宜/可”的差别；正文要求与附录的指南、示例分开。附录表 A.1 的“×”是指南中的阶段标记，不能单独解释为禁止。剪裁理由及约定须纳入合同等文件，不能由技能替订购方批准。来源：02，§4.6.3、5.2、A.2~A.3，PDF 10、12、27~28。
- **角色和编号**：编制计划时，201对应订购方测试性计划，202对应承制方/转承制方测试性工作计划。沿用2012版编号或遇到附录302分配引用时，用现版正文定位303，并注明原文疑义。来源：03、00，§6.1~6.2、7.3，PDF 13~14、19、35。
- **指标口径**：计算前区分故障率加权预计与事件计数评估，并明确故障集、可更换单元、维修级别、测试方法和隔离模糊度。FIR分母是已检测故障；FAR分母是报警次数。参数越界、集合不一致或零分母时停止该项计算并说明缺口。来源：07，A.6.2.4.4、A.7.2.3.9，PDF 48~49、57。
- **达标证据**：需要合格结论时，核对合格判据、验证时机/方法、样本和统计方案。预计或点估计不能自动替代单侧置信限；不能做实物试验或试验不能考核的要求按402处理，证据不足列为“无法确认”。来源：05、07，§4.7、8.2、8.3.2.7及附录A.7，PDF 10、23~25、54~57。
- **虚警归因**：处理不能复现CND、重测合格RTOK时，保留原始故障与检查记录，分析间歇故障、BIT、容差及维修过程。不能把所有CND/RTOK直接计为虚警。来源：06、07，A.4.2.1.10.2、A.8.2.1，PDF 34、58。
- **变更闭环**：发现缺陷或技术状态变化时，更新模型、预计、准则、诊断和验证，追踪措施及有效性证据；新增或剪裁工作项目沿合同/订购方确认途径处理。来源：03~06，§6.6、7.2~7.7、8.1~8.3、9.2。
- **引用范围**：需要引用标准的具体程序、样本量或统计表时，取得该标准适用版本的原文；本包的全文与范围核验等级以09和标准索引为准。需要判断最新版时，另外检索正式发布信息。来源：01、00，§2，PDF 6。

## 输出最小信息

普通软件与领域建模按10/11交付必要的范围、统一语言、模型约束、需求/验证设计、追踪、证据状态和待决事项；领域建模任务包含愿景、术语、上下文、聚合/行为/不变量、事件、hotspots和后续动作。简单用例任务交付可执行设计即可。装备任务使用[08的模板](resources/08-模板与案例.md)，保留对象/阶段/角色、依据、假设、页码、计算、证据与未决事项。审查结论区分满足、不符合、证据不足；计算脚本只给预计或点估计，不输出合格认证。

在技能目录可运行`python3 scripts/lookup.py --standard "IEEE 1012-2024"`查标准元数据，`--term TestRun`查规范词TestExecution及别名，`--query 统一语言`查资源文字；`--item 304`始终查GJB现版项目。MIL正文见[PDF](assets/mil-hdbk-2165-1995.pdf)及[确认通知](assets/mil-hdbk-2165-notice3-2024.pdf)，不套用GJB页码偏移。
