# 软件需求与验证设计

本资源是测试性、需求追踪及证据管理思想的软件工程**适配**，不是 GJB 2547B 对一般软件新增的强制条款，也不代表 MIL、IEEE 标准间等效。标准范围与引用深度见 [09-多标准对照](09-多标准对照.md)；概念关系见 [10-领域模型与统一语言](10-领域模型与统一语言.md)。下列术语是工程工作定义；引用具体标准条款须取得适用原文，区分原文要求、参考方法和项目约定。

## 选择工作对象

| 模式 | 被设计的对象 | 主要交付物 |
|---|---|---|
| A：研发测试或验证工具 | 测试管理平台、用例设计器、执行器、诊断工具、证据与报告系统等软件产品 | 领域模型、统一语言、可验证需求、规则与状态、架构与 API、界面行为、工具自身的验证方案 |
| B：为普通软件设计测试或验证活动 | 业务 API、应用、服务、基础设施组件 | 单元、集成、API、系统、验收、性能或韧性测试设计；用例与规程、环境、执行记录、证据、判定及结论 |

两种模式可以并用，但须标明需求对象：“执行器记录版本”属于 A，“支付 API 重复请求仅扣款一次”属于 B。工具运行成功不等于被测产品满足需求；工具通过自身验证也不等于预期用途得到确认。

软件测试性关注可观察、可控制、可隔离、可替换依赖、可重现及可恢复能力，如稳定时钟、依赖替身、关联标识、状态查询及数据清理。按风险和成本选取。装备 FDR、FIR、虚警及其门限不能普遍替代代码覆盖率、业务正确率、可用性或性能目标；确实适用时，另行定义故障集、分母、条件及验收依据。

## 统一语言与最小流程

沿用 10 的术语，不将“结果”“证据”“判定”“结论”混作一个状态字段：

| 中文／英文 | 本资源中的用途 |
|---|---|
| 需求 Requirement | 对对象应有行为、约束或质量属性的陈述，带来源和适用版本 |
| 验证 Verification | 用客观证据判断规定要求是否满足 |
| 确认 Validation | 用客观证据判断对象是否满足预期用途和相关方需要 |
| 测试设计 TestDesign | 依据目标、风险及模型确定测试条件、覆盖策略和判据 |
| 测试用例 TestCase | 针对特定条件的输入、动作及预期结果；不与执行记录合并 |
| 测试规程 TestProcedure | 为实施用例而确定的准备、顺序、操作、采集及清理步骤 |
| 执行 TestExecution | 在确定对象、环境和配置上实施规程的一次活动；TestRun为兼容别名 |
| 观察 Observation | 实际采集的状态、响应、日志、测量等事实 |
| 结果 TestResult | 本次观察、测量和步骤结果的结构化记录，可引用判定；不等于执行状态或整体验收结论 |
| 证据 Evidence | 能支持某项主张、具有来源与上下文的记录及其关联 |
| 判定 Verdict | 按既定判据对特定结果给出的通过、失败等决定 |
| 结论 Conclusion | 综合范围、证据及限制，对需求或预期用途的满足程度作出的主张 |

按需细化；简单 API 可用词典和状态表，无须强建多个限界上下文或聚合。

1. **概念层 → 统一语言**：说明谁在何种情境达成什么目标，列出对象、行为、事件及歧义。区分业务与工具术语，指定上下文、定义、同义词和禁用混称。数据库表、页面和接口是后续映射，不作为概念定义起点。
2. **规则与状态**：把关键不变量、允许的命令、前置条件、状态迁移、失败与恢复路径写清。复杂并发或跨系统一致性确有需要时，再定义聚合边界、领域事件和上下文关系；不以 DDD 术语数量评价设计质量。
3. **需求可验证化**：将模糊表述拆成条件、行为和判据，补足观测点、验证方法与边界。预期用途对应确认目标，不直接等同技术接口断言。
4. **设计与执行**：按规则和风险选择正常、边界、异常、并发及恢复条件，明确层次、替身、数据、环境和判据。由用例形成规程，再记录每次执行；按需自动化。
5. **证据与结论**：关联原始观察、比较结果、判定和缺陷，逐项说明覆盖、未覆盖及证据限制。修改模型、需求或软件后做影响分析，选择受影响的复核与回归。

## 输入 → 处理 → 输出

| 输入 | 处理 | 输出 |
|---|---|---|
| 目标、用户旅程、需求来源、术语与现有材料 | 范围澄清、概念归并、冲突与未知登记 | 词典、概念关系、范围及假设 |
| 业务规则、状态、架构或接口草案 | 规则实例化、可验证化、风险分析 | 需求条目、状态表、测试条件与待决策项 |
| 对象基线、环境和资源、判据 | 设计用例与规程，执行并采集 | TestDesign、TestCase、TestProcedure、TestExecution、Observation |
| 原始记录、比较规则、缺陷与偏差 | 复核来源、评估覆盖和证据充分性 | TestResult、Evidence、Verdict、Conclusion、回归范围 |

只有部分材料时，先完成草案和缺口清单，记录未知、负责人及影响。执行证据与最终结论是后续产物，不能作为开始设计的前置材料。影响关键判据或行动的未知仅阻止相关结论或执行，其余工作继续。

### 将概念一致性变成验证对象

先按 [10 的上下文与事实所有权](10-领域模型与统一语言.md) 确认模型，再把语义映射写成可观察的契约。用同一条业务旅程检查需求、API、UI 和报告是否表达同一个概念；相同名字但身份、状态或规则不同仍然是冲突。以下是工程设计检查，非标准新增要求：

| 待验证的模型规则 | 正常与反例 | 可观察判据 |
|---|---|---|
| 用例设计与一次执行身份分开 | 用例发布新版本；已有失败后重跑 | 新执行有新身份；旧执行仍引用原设计、判据和配置版本 |
| 执行生命周期与判定分开 | 正常完成但观察不满足判据；进程退出零但证据缺失 | 前者完成且失败；后者保留结束事实且无法判定，均不能显示为验收通过 |
| 跨上下文事实由契约转换 | 外部 `success` 只代表传输成功；收到未知状态或缺版本事件 | 保存原值、来源和错误原因；未知语义待核验，不猜测本地判定、不反写上游事实 |
| 集成事件不改变业务身份 | 重复提交同一事件；先收到新修订再收到旧修订 | 同一事件不重复登记；旧事件不回退已知版本，具体乱序处置按契约验证 |
| 评价结论有独立范围和证据 | 一项执行通过，但另一个目标缺少证据 | 结论明确未覆盖目标和限制，不把局部通过扩大为产品合格 |

概念/术语变更时，同时检查状态迁移、业务不变量、事件和字段语义、历史版本解释、外部映射及验证判据。需要兼容旧字段时保留版本化适配；只改界面标签不能完成模型迁移。普通软件采用其业务模型的同类场景，不必强套测试平台对象。

### 需求条目 schema

字段可简写，阈值无来源不得默填；多项独立行为拆分，保留上位需求。

| 字段 | 内容 |
|---|---|
| `id / revision / status` | 稳定标识、修订号、草案或基线状态 |
| `object / context` | 对象、边界、参与者、适用配置与用途 |
| `source / rationale` | 原始需求或标准版本及条款、业务理由；工程建议明确标注 |
| `condition` | 初始状态、输入、前置条件、并发或时间条件 |
| `behavior` | 应发生及不得发生的可观察行为 |
| `criterion` | 可判定标准、容差、时间窗、统计口径及目标的来源 |
| `observation` | 观察点、采集方法、标识关联及所需精度 |
| `trace` | 上位目标、规则、设计、接口、用例及证据标识 |
| `method / level` | 测试、分析、检查或演示，以及单元至验收等实施层次 |
| `boundary` | 适用与不适用条件、替身限制、异常及恢复边界 |
| `unknowns` | 未决项、假设、责任方；对判据或结论的影响 |

## 追踪、基线与证据充分性

采用多对多关系：一个需求可由多个用例和分析证据支持，一个用例也可覆盖多个需求。不要仅用“已关联用例”代表覆盖充分。

| 需求及版本 | 规则／状态 | 设计条件 | 用例／规程版本 | 执行与对象基线 | 证据／缺陷 | 判定与需求结论 |
|---|---|---|---|---|---|---|
| REQ-ID@r | 规则 ID／迁移 | 条件及边界 | TC-ID@r／TP-ID@r | RUN-ID、构建、环境 | EV-ID、来源、限制 | Verdict；Conclusion、剩余风险 |

证据应回答“证明什么、来源和条件是什么、按什么判据、能否复核”。记录构建或提交、需求和用例版本、环境／依赖／数据、时间、执行者或工具版本、原始文件位置和采集方式。按需附哈希、时钟误差、采样率及脱敏说明。哈希只能支持完整性判断，不能单独证明真实性或要求满足。

执行状态与判定分开：执行状态可为待执行、运行、完成、阻塞或中止；规则判定可为通过、失败、无法判定或不适用，具体枚举由项目约定。外部工具把阻塞/未执行混在结果枚举中时，保留外部值并在适配层映射，不将其解释为通过。结论使用“满足所述要求／不满足／证据不足”，并写明范围。空结果、日志缺失、对象版本不明、仅有预测或替身结果超出代表范围时，不得汇总通过。性能与概率性结论还需样本、时长、统计方法及不确定性；通过不证明未覆盖场景正确。

保留历史执行与证据；新版本建立新关联，标记旧结论范围。需求、模型、API、规程或判据变更均做影响分析，不能重命名旧执行冒作新执行。实际代码重命名、数据库变更、生产故障注入及外部写入仍遵循当前任务范围、工程约束和既有授权。

## 示例一：支付 API 的幂等性

以下为**合成项目约定，非标准门限**。范围为模拟账本的支付 API，第三方结算另验。词典：支付意图为业务请求，幂等键标识提交意图，支付交易为执行结果；重复请求不等于新交易。R-PAY-1：同商户、同键、同规范化载荷对应同一交易；同键异载荷拒绝。

- **REQ-PAY-01@1**：同商户、账户有效且余额充足，首次请求后 24 小时内同键同载荷重试（含并发及响应丢失），返回相同交易标识，账本仅一条借记；同键异载荷返回约定冲突码且不新增借记。24 小时为项目约定。过期键行为未知，单列 REQ-PAY-02 草案。
- **设计**：状态为未受理→处理中→成功或失败，区分外部超时与已失败。TC-PAY-01 顺序重复，02 同时发起 20 次，03 在提交成功后丢失响应再重试，04 改变金额后重用键。20 为合成测试负载。接口观察交易 ID，账本查询确认副作用，关联标识连接请求与日志。
- **规程与执行**：TP-PAY@1 先建立隔离账户和余额快照，执行各条件，收集请求／响应、交易和账本记录，最后清理。RUN-PAY-01 绑定构建 b17、账本版本和替身配置；EV-PAY-01 保存观察，TestResult 比较标识和借记数量。若仅有重复 HTTP 成功响应而无法查看账本，只能确认响应一致，资金副作用证据不足。
- **结论规则**：所有约定条件满足才可在该范围判定通过；本例未提供实际执行记录，执行状态为“待执行”，需求结论为“证据不足”，不能宣称支付幂等性已验证。

## 示例二：测试平台从验证目标到证据

模式 A，状态为**合成项目约定**。VO-01：“报告可追踪到执行时的需求和规程”。区分 TestCase 可复用设计、TestProcedure 实施步骤、TestExecution 一次执行；编辑用例不修改历史执行。

- **REQ-PLAT-01@1**：执行开始时保存需求、用例、规程、对象及环境版本；编辑用例后，历史详情和报告仍展示原版本，能定位证据。观察包括 API 响应、快照、报告和文件清单。报告须包含证据或可访问的关联及保留规则。
- **领域与接口**：设计管理负责设计版本，执行管理负责运行及证据引用，评估负责判定和结论；可在同一应用实现。`startExecution` 固定版本；编辑生成新修订；`recordObservation` 关联运行；`evaluate` 记录判据版本。界面区分草案与历史运行，避免仅显示“最新”。
- **TC-PLAT-01／TP-PLAT@1**：创建需求 r1、用例 c1 和规程 p1→开始运行→将用例改为 c2→记录观察并导出→比较详情与报告。预期仍引用 c1；另测缺证据、失败执行、无权访问证据及并发修改。执行成功但版本漂移应判失败，不能用“已完成”覆盖缺陷。
- **确认目标**：让目标角色用报告复核一次争议结果，检查能否理解依据并找到证据；这是预期用途的确认活动。接口测试可证明版本字段正确，不能单独证明报告足以支持用户决策。此例为设计草案，真实可用性确认仍待实施。

## 示例三：性能与故障注入

模式 B，以下均为**合成项目约定，非标准门限**：订单查询在规定测试环境、固定数据集和 200 个并发用户下，预热后持续 30 分钟，服务端成功请求 p95 延迟≤300 ms，错误率≤0.5%；缓存中断后允许降级，并在依赖恢复 60 秒内恢复约定服务水平。

设计正常负载、缓存不可用、依赖恢复三个条件，记录请求分布、并发模型、预热、时间窗和分位算法；按本需求口径统计成功请求的延迟，同时单列全部请求的超时与失败并计算错误率，失败请求不能从错误率分母删去。TestProcedure 固定构建和环境、隔离范围及清理方案，采集原始样本、关联日志、故障及恢复时间。故障注入仅在授权目标和环境执行。

TestExecution 保存窗口和观察，TestResult 分别比较延迟、错误率和恢复时间。样本丢失或时间关联失真时判证据不足。单次通过仅支持该负载与环境下的结论，不能外推全年可用性、生产容量或全部故障组合。无真实记录时仅输出设计和待验证清单。
