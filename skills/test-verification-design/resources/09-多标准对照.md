## 软件工程、领域模型与统一语言

软件测试设计、验证设计可以复用“要求→模型→设计→评价→证据→改进”的结构；是否适用某项标准条款须另作判定。以下均为本技能的工程建模建议，不是IEEE或GJB正式定义。

普通软件任务优先以29148梳理需求和可验证性，以29119-1研究测试概念，以1012研究V&V范围，再按需引入GJB/MIL诊断设计和证据闭环。V&V不应缩减为执行测试；IEEE1012公开范围还包括分析、评价、评审、检查和评估。领域模型中分别表达“与规定要求的关系”和“与预期使用/用户需求的关系”，具体术语、过程及强制交付物须全文核验；不能据公开摘要声称已实现这些标准规定的完整V&V流程。

| 来源主题 | 软件工程迁移 | 领域模型与统一语言的约束 |
|---|---|---|
| 要求及剪裁、计划和评审 | 明确产品、风险、阶段、交付物、责任、验证策略 | 区分需求、质量目标、验收判据、适用决策；每项有来源和版本 |
| 故障—检测—隔离与诊断模型 | 建立缺陷/故障假设、激励、观测、判定依据、定位关系 | 区分缺陷、故障、失效、症状、观测、诊断结论；候选词义由领域方确认 |
| 内建/外部测试与接口 | 考虑测试接口、可观测性、可控性、诊断边界 | BIT不自动等于单元测试；日志、追踪也不自动构成检测或验收证据 |
| 指标预计及评价 | 建立指标契约及测量证据 | 保存故障集/场景集、分母、权重、观测窗口、环境及版本；代码覆盖率不等于FDR |
| 结果、会话、维修行动数据 | 关联测试运行、环境、结果、缺陷、修复及复测 | 测试用例定义与执行实例分开；结果与证据分开；修复与验证通过分开 |
| 增长与使用反馈 | 用生产事件和回归证据更新风险及设计 | 变更可追踪到需求/模型/测试/证据；不能仅以重测通过推断原报警为虚警 |

LRU/SRU、维修级别、BIT/ATE、隔离模糊度、故障率权重及FDR/FIR/FAR在装备诊断语境中有特定意义。普通软件系统只有在明确对象和语义后才建立候选对应，不强行把服务、模块或微服务命名为可更换单元。不能直接迁移资料性门限、抽样方案、合同角色或鉴定程序。软件测试的领域划分、业务不变量、测试判定依据与验证证据应先由本项目统一语言定义，再标注外部标准的参考关系。

## 对照输出与冲突处理

每条对照至少输出这些字段，可作为表格或JSON记录：

```json
{
  "comparison_id": "CMP-001",
  "topic": "诊断模型",
  "source": {"standard": "GJB-2547B-2024", "clause": "7.2", "pdf_pages": [18, 19]},
  "target": {"standard": "IEEE-1232-2010", "clause": null, "pdf_pages": []},
  "evidence_type": "engineering_mapping",
  "source_evidence": "fulltext_verified",
  "target_evidence": "official_scope_status_only",
  "relationship": "related_concept",
  "applicability": "candidate",
  "differences": ["IEEE具体数据模型待全文核验"],
  "project_decision": null,
  "owner": null,
  "status_checked_at": "2026-10-15"
}
```

需要逐条比较时补充：对象/层次、阶段/责任方、条文强度和剪裁、输入/活动/输出、指标分母/权重/单位、验证方法/样本/置信限、接口/数据字段、证据位置及待办。`relationship`可取`related_function`、`related_concept`、`partial_overlap`、`no_direct_counterpart`；只有双方法定文本和适用上下文均核验后，才论证更强的一致性结论。

冲突处理顺序：确认双方版本及证据→辨认词义/对象/统计集合差异→检查项目适用依据和合同剪裁→输出影响与待决策项。不同标准的同名术语分别保留命名空间和定义来源；不能合并成一个词而丢失语义。没有明确优先规则时，由项目责任方确认，不自行取更严格数字，也不把旧标准状态当作技术内容自动无效或现行合规依据。
