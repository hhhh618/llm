# 验收与评测

用于定义完成条件、设计用例、比较候选或建立回归流程。简单任务可只保留一句成功条件和一次核验。

## 任务契约

按需要填写，复用项目已有需求、测试与预算：

```yaml
# 概念模板，不是 SDK 配置；示例值需按当前任务替换。
task_id: research-example
objective: 回答指定主题，并交付可追溯结论
scope: 用户指定的时间范围、来源及输出边界
deliverable: 报告或产物引用
acceptance:
  result: 关键结论由实际打开的来源支持
  process: 来源与操作均在任务允许范围内
  completion: 产物可读，必要核验完成，未知项明确列出
budget:
  deadline: 由任务要求确定
  calls_or_cost: 需要控制成本时设定
stop_conditions: 预算耗尽、关键输入缺失或修正不再产生进展
```

不要把代理自述的“完成”、HTTP 200、格式正确或另一个模型的赞同，直接当成完整任务成功。

## 验收层次

| 层次 | 检查什么 | 可用证据 |
| --- | --- | --- |
| 步骤 | 工具选择、参数、结果契约、错误处理 | 校验器、工具结果、单步测试 |
| 最终结果 | 业务终态、产物行为、事实支持与覆盖 | 数据库状态、运行测试、引用位置、回执 |
| 过程约束 | 授权、目标、必要确认、路由与资源边界 | 动作记录、审批决定、可观察调用轨迹 |
| 重复与运营 | 多次执行稳定性、耗时、成本、恢复 | 独立 trials、运行统计、故障注入 |

终态正确不证明过程符合约束；工具调用轨迹正确也不证明产物可用。两者按任务分别核验。

## 用例与评分

1. 从代表性真实任务与失败样本开始，标明输入、预期结果和关键约束。
2. 保留独立测试集，避免所有样本同时用于改 prompt 和报告泛化成绩。
3. 覆盖正常、边界、缺失输入、错误工具结果；涉及长任务或写操作时增加恢复场景。
4. 尽可能使用测试、schema、状态差异及引用核验。需要 LLM judge 时提供明确 rubric、正反例并用人工判断校准。
5. 对开放任务评估允许的结果与约束；只有工具顺序本身属于要求时才严格匹配路径。
6. 运行多次时重置环境，避免上一轮文件、缓存和业务状态污染结果。

样本量与通过门槛由业务损失和任务差异决定。小样本可帮助诊断；不得据此宣称整体可靠性已得到充分证明。

## 比较单 Agent 与候选方案

候选使用相同任务、验收条件、工具与数据权限。报告模型与版本；区分相同资源预算下的质量比较，与达到同等质量所需成本的比较。

至少记录：

- 通过验收任务数 / 总任务数，并查看重要任务子类。
- 关键约束违规、漏报与误报，视领域选择。
- 重复执行稳定性；需要时使用逐任务的 pass^k。
- 完成耗时，区分模型、工具和人工等待。
- 总执行成本 / 通过验收任务数，包含失败和重试；无成功样本时报告无定义及总成本。
- 模型与工具调用数、人工介入、恢复成功率及重复副作用。

`pass@k` 关注至少一次成功；`pass^k` 关注同一任务的 k 次独立试验全部成功，再跨任务平均。两者不可混用，也不要用全部任务平均成功率的 k 次方替代逐任务估计。

## 持续评测与交付记录

对持续运行的系统，在 prompt、模型、工具或编排变更后运行相关回归；线上失败经脱敏和核验后加入用例。将评分回连到失败步骤，确定修复对象。

结果表可以简化为：

| 用例 / 版本 | 结果与过程是否通过 | 证据 | 耗时 / 成本 | 失败分类 | 下一步 |
| --- | --- | --- | --- | --- | --- |
| 当前运行 | 通过 / 失败 / 待验证 | 测试、状态或产物引用 | 实测或未测 | 具体原因 | 修复或继续验证 |

无法运行的比较应交付评测方案和缺失条件，并准确标为未实测。一次性小任务不需要为了使用本技能建立 CI 或监控平台。
