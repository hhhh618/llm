# 按需并行

用于判断分工收益、选择协调模式、委派与合并。增加 Agent 是需要证据的优化项；没有可比基线时保留不确定性。

## 选择条件

优先考虑独立研究方向、独立只读审查、不同上下文或权限边界。每个子任务应能独立交付有用结果，并有明确验收方法。

强依赖、频繁共享可变资源、反复交换大量上下文的步骤适合有序执行。不要用角色名称替代分工设计。用户指定拓扑时沿用其选择并解释可观察的取舍，不能自行改换产品或架构。

| 模式 | 控制与责任 |
| --- | --- |
| 固定顺序 | 程序决定下一步，适合依赖明确的阶段 |
| 并行分支 + 汇总 | 独立工作并发，汇总者核验覆盖并解决冲突 |
| Manager + agents as tools | 主负责人保留交付责任，专家完成边界清楚的子任务 |
| Handoff | 接收者接管后续工作；限定转交关系，防止循环 |
| Evaluator–optimizer | 评价标准明确，缺陷反馈能指导有限修正 |

## 委派契约

按任务需要简化，不让每个专家重读完整历史：

```yaml
# 概念模板，不是宿主工具参数。
task_id: review-example
objective: 一个明确问题或可独立交付的结果
inputs: 必要事实、文件及已有证据引用
scope: 可以读取、修改的资源与工作边界
output:
  result: 结论或产物引用
  evidence: 测试、来源、位置或系统回执
  uncertainties: 尚未核验的部分
  status: completed | needs_input | failed
budget: 按任务设定
acceptance_owner: 负责检查并合并结果的人或主 Agent
```

主负责人检查实际产物与证据，处理互相矛盾的发现，确认是否遗漏范围。专家摘要不能替代关键证据核验，也不能自动继承更大的操作权限。

## 共享资源与写入

- 独立读取、分析和输出到不同文件可并行。
- 修改同一文件、订单、数据库记录等资源时，明确所有者或先产出独立补丁，再由指定合并者整合。
- 有依赖的写操作保持顺序或使用应用本身的事务 / 版本检查。
- 并发限制受工具配额、总预算和上下文合并成本约束。
- 某分支失败时保留已验收成果，避免无差别重启所有工作。

## 如何证明值得保留

使用同一任务集、验收标准与可比资源预算，比较质量、漏报 / 误报、稳定性、成本和墙钟时间。并行加快等待不必然降低总成本；更多上下文和协调可能抵消收益。

独立评审需要明确缺陷标准和证据。评审者同意生成者，不等于已验证；能运行测试、核验引用或检查业务状态时使用这些证据。

如果本次只交付设计，提出比较方案即可；不要把预期收益写成实测结果。评测细节见 [验收与评测](acceptance-and-evaluation.md)。
